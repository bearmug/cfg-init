## Delegation policy

Main owns scope, decomposition, shared contracts, integration, verification, and user communication. These are main's orchestration rules; subagents execute only their assigned role and scope, report evidence and blockers, and do not spawn agents.

- **Placement:** Delegate when context isolation, useful parallelism, lower-cost sufficient reasoning, or independent expertise outweighs handoff and verification overhead. Use benefit-based decisions rather than blanket startup-scout/final-review stages or a minimum worker count: one substantial evidence-heavy investigation can justify one worker. Keep trivial, localized work and existing-context answers inline; never pad tasks.
- **Scope:** Inspect enough to define a bounded assignment and interfaces, then let its worker own the necessary exploration or implementation. Do not duplicate delegated work or outsource main's integration responsibility.
- **Selection:** Choose workers by required capability and configured cost using the model tiers below: economical for mechanical work or extraction, ordinary capability for routine repair, stronger reasoning for consequential ambiguity. Capability tiers alone do not prove price or savings. Respect explicit model/provider pins; check the resolved model and any fallback, and stop/disclose unauthorized substitutions. Honor user delegation bans, disabled roles, concurrency limits, and host approvals.
- **Parallelism:** Dispatch ready, genuinely independent substantial slices together through the chosen interface: one native `tasks[]` batch for native agents, concurrent app-owned calls for T3 child tasks. Define shared contracts and one writer per mutable path/resource, including main; serialize real dependencies. Do not edit active workers' owned paths without explicitly recovering ownership.
- **Briefs:** Every assignment must include the user objective, necessary context/evidence references, constraints and non-goals, owned paths, interfaces, deliverable, and acceptance criteria. Workers do not inherit main's conversation. Keep bulk evidence worker-side; require concise, actionable findings and recoverable references, not raw dumps.
- **Expertise:** Seek read-only expert advice or independent review on explicit request or consequential uncertainty remaining after targeted retrieval. Missing evidence calls for retrieval, straightforward failed checks for repair, and malformed reports for correction—not automatic escalation. Expert planning does not imply expensive execution or another review; implementation stays with the authorized writer.
- **Coordination:** While workers run, do distinct useful work or use native wait; do not poll or launch duplicate work. Reuse retained evidence and worker findings instead of rediscovering them; reopen only material gaps or changed assumptions.
- **Acceptance:** Require status, findings/changes, checks actually run, evidence references, uncertainties, and blockers. Check results against their criteria, correct gaps, integrate once, and verify the combined behavior. Worker completion or a favorable review never substitutes for final acceptance; report unverified requirements explicitly.

### Model tiers (native `task` and T3)

Pick the subagent model by setting the per-item `agent` field. Each tier agent is a full-capability worker (`~/.omp/agent/agents/<name>.md`, model via `modelRoles.<name>`, thinking `auto`, no retry fallback).

| Tier | Codex sub | Claude sub | Use for | Saves |
| --- | --- | --- | --- | --- |
| easy | `easy-luna` (GPT-6 Luna) | `easy-haiku` (Haiku 5.5) | mechanical edits, renames, extraction, data collection, fully specified routine changes | lots of money + main context |
| mid | — | `mid-sonnet` (Sonnet 5.5) | bounded implementation/repair needing some judgment, multi-file but well-scoped | some money + main context |
| high | `high-sol` (GPT-6.1 Sol) | `high-opus` (Opus 5.5) | unknown causes, hard bugs, consequential design, integration-sensitive changes | main context |

- Default to the cheapest tier that can meet the acceptance criteria; escalate one tier on a failed or malformed result, not preemptively.
- Provider choice within a tier: honor user pins; otherwise spread load across Codex and Claude subs, preferring whichever has quota headroom. A tier agent never falls back to another model; on a usage-limit failure, re-dispatch to the sibling agent in the same tier and say so.
- `solutionSpace` drives the child's `auto` thinking level: keep it honest (narrow for given fixes, open for unknown causes).
- Read-only research with unknown file locations still goes to `scout`; review to `reviewer`. Tier agents are for doing work.
- Report the resolved model badge when it differs from the requested tier.

### T3-specific delegation

- **Two routes:** In T3 the coordinator may delegate (a) app-owned through `~/.local/share/cfg-init-feedback/t3_policy.py delegate` (assignment JSON on stdin): a visible T3 child task with catalog validation, resolved-model verification and audit; or (b) native `task`: runs inside this thread as tool calls, invisible to T3 task status/cancel/history, no helper audit, so check the resolved model badge yourself. Prefer (a) when the user needs T3 visibility/management; (b) when in-thread results or lower overhead matter, or when the user asks. Never create ordinary threads to impersonate child tasks. Outside T3 use native delegation with the same selection and worker rules.
- **Visible native subagents:** Native `task` agents render only as inline tool calls, so mirror each one in `todo` under a `Subagents` phase: one item per agent, `<Name> (<agent tier>): <short goal>`, appended (or init) in the same turn as the spawn, marked done when its result is accepted and dropped if it fails or is cancelled (re-dispatches get a new item). App-owned T3 child tasks already show as task cards; do not mirror them.
- **Tier lanes:** The T3 `lane` field takes the same tier names as the native agents (`easy-luna`, `easy-haiku`, `mid-sonnet`, `high-sol`, `high-opus`) and selects the same OMP model with thinking `auto`, mode `default`, whichever OMP model the coordinator thread itself runs. Apply the tier rules above. Omitted `lane` means `high-sol`: unknown causes, sequential bugfixes, consequential ambiguity and integration-sensitive changes stay there unless the user says otherwise. Any other lane requires a `reason`. No price/savings claim follows from a capability label.
- **Explicit pins:** User pins override defaults. Lane `pinned` takes an explicit `target` `{"providerInstanceId", "model", "options"}` and a reason, for selections outside the tiers (e.g. a fixed thinking level). The helper rejects models or options T3 does not list. Cross-harness work is an explicit exception, not an inherited accident. Never silently substitute or fall back; unavailable selection is a blocker; on a usage-limit failure, re-delegate to the same-tier sibling lane and say so.
- **Assignment and audit:** Supply `task`, `[sub] [topic] short goal` title, role and stable per-round `clientRequestId`, plus `lane` and `reason` when non-default. Include the objective, source references, constraints, owned paths, shared interfaces, deliverable and acceptance. The helper validates catalog selection, verifies resolved provider/model/options, cancels unverified launches and records routing metadata (not task bodies or credentials) in `${XDG_STATE_HOME:-~/.local/state}/cfg-init-t3/delegations.jsonl`. Retain task IDs and consume actual results; no polling.
- **Coordinator-only interaction:** Workers never spawn agents/threads, ask the user, open dialogs, resolve approvals or continue via direct user messages. Return `BLOCKED` with the question, options/tradeoffs, evidence and any required permission to the coordinator. Coordinator asks once in the main conversation and delegates a new bounded round with the answer. Do not send follow-up turns to the backing child thread. Security approvals are never assumed, auto-accepted or widened.
- **Runtime boundary:** The configured ACP relay rejects additional worker prompts and cancels worker question elicitations rather than displaying dialogs. Security permission requests and responses remain unchanged and host-owned; cfg-init cannot move those approvals into the coordinator UI. The OMP extension treats T3 workers, native subagents (`ctx.agent.kind !== "main"`) and unverified sessions as workers: it blocks their native spawning and child interaction tools, so only the main coordinator session may spawn natively; it blocks direct `delegate_task` for everyone; helper refuses child delegation using host lineage. These are cooperative integration guards, not a sandbox for unrestricted shell code or other harnesses. T3's composer visibility is host-owned; do not claim this configuration hides it. Child chat-specific instructions are not inherited: include necessary constraints in every brief.
- **Verification:** Main exercises the consumer-visible path after integration. A completed child or favorable review is not acceptance. Check requested vs resolved selection and report unverified host boundaries explicitly.

## Notifications

When the user asks to be notified, send one Telegram message after verified completion: `tg-notify 'done: <one-line summary>'`. Main sends it, not workers. Never read or print `~/.config/tg-notify/env`. Report a send failure; do not retry.

## T3 Code thread naming

When running in T3 Code, name threads `[subject] specific goal`. The bracketed subject must be one lowercase word naming the durable topic, not a workflow status or generic role. Reuse consistent subject vocabulary. Follow it with a short specific goal; use 3–6 words overall and aim below 40 characters. Name the durable user goal, not the current phase, latest finding, tool, or completion state. Omit redundant project names and status labels. Never use a bracketed label alone. Examples: `[feedback] prevent repeat complaints`, `[threads] consistent naming`, `[sidebar] compact project tree`.

For the current thread, use the T3 thread metadata rename tool once the goal is clear only if its title is a known placeholder or automatically generated title. Never rename a deliberately/manually user-set title unless the user explicitly asks, even if it violates this convention: preserve `[Coordination]` exactly, including capitalization and its bracket-only form. If title provenance is uncertain, leave it unchanged. Keep an accurate compliant title stable unless the user changes the durable goal. Rename metadata only; never change workspace, project placement, status, or branch as part of naming.

When creating a delegated subagent thread, put the short marker `[sub]` at the very left, before the topic: `[sub] [subject] specific goal`, for example `[sub] [sidebar] compact project tree`. This prefix is required for newly created subagent titles; ordinary top-level threads do not get it. Preserve manually user-set titles rather than retroactively adding the prefix. Supply a compliant explicit title when creating or delegating a T3 thread wherever the API supports it. Do not create threads merely to name them, add a polling renamer, or rename unrelated existing threads without user authorization. This policy applies to OMP agents; it does not configure T3's independent automatic title generator or other providers.
