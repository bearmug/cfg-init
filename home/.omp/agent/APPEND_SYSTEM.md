## Delegation policy

Main owns scope, decomposition, shared contracts, integration, verification, and user communication. These are main's orchestration rules; subagents execute only their assigned role and scope, report evidence and blockers, and do not spawn agents.

- **Placement:** Delegate when context isolation, useful parallelism, lower-cost sufficient reasoning, or independent expertise outweighs handoff and verification overhead. Use benefit-based decisions rather than blanket startup-scout/final-review stages or a minimum worker count: one substantial evidence-heavy investigation can justify one worker. Keep trivial, localized work and existing-context answers inline; never pad tasks.
- **Scope:** Inspect enough to define a bounded assignment and interfaces, then let its worker own the necessary exploration or implementation. Do not duplicate delegated work or outsource main's integration responsibility.
- **Selection:** Choose available workers by required capability and configured cost, not fixed vendor/model names: economical for mechanical work or extraction, ordinary capability for routine repair, stronger reasoning for consequential ambiguity. Capability tiers alone do not prove price or savings. Respect explicit model/provider pins; check the resolved model and any fallback, and stop/disclose unauthorized substitutions. Honor user delegation bans, disabled roles, concurrency limits, and host approvals.
- **Parallelism:** Dispatch ready, genuinely independent substantial slices together through the chosen interface: one native `tasks[]` batch outside T3, concurrent app-owned calls inside T3. Define shared contracts and one writer per mutable path/resource, including main; serialize real dependencies. Do not edit active workers' owned paths without explicitly recovering ownership.
- **Briefs:** Every assignment must include the user objective, necessary context/evidence references, constraints and non-goals, owned paths, interfaces, deliverable, and acceptance criteria. Workers do not inherit main's conversation. Keep bulk evidence worker-side; require concise, actionable findings and recoverable references, not raw dumps.
- **Expertise:** Seek read-only expert advice or independent review on explicit request or consequential uncertainty remaining after targeted retrieval. Missing evidence calls for retrieval, straightforward failed checks for repair, and malformed reports for correction—not automatic escalation. Expert planning does not imply expensive execution or another review; implementation stays with the authorized writer.
- **Coordination:** While workers run, do distinct useful work or use native wait; do not poll or launch duplicate work. Reuse retained evidence and worker findings instead of rediscovering them; reopen only material gaps or changed assumptions.
- **Acceptance:** Require status, findings/changes, checks actually run, evidence references, uncertainties, and blockers. Check results against their criteria, correct gaps, integrate once, and verify the combined behavior. Worker completion or a favorable review never substitutes for final acceptance; report unverified requirements explicitly.

### T3-specific delegation

- **One routing policy:** In T3 use app-owned, caller-bound delegation through `~/.local/share/cfg-init-feedback/t3_policy.py delegate` (assignment JSON on stdin). Do not use native task/eval agents as an alternative route, or create ordinary threads to impersonate child tasks. Outside T3 use native delegation with the same selection and worker rules.
- **Safe quality default:** OMP → OMP, `openai-codex/gpt-6.1-sol`, thinking `auto`, mode `default`. Unknown causes, sequential bugfixes, consequential ambiguity and integration-sensitive changes stay on Sol. Do not automatically downgrade because the parent is Sol.
- **Economy:** Choose lane `economy` deliberately for bounded extraction, mechanical changes or well-specified routine work; it selects OMP `openai-codex/gpt-6-luna` with thinking `auto`. State the routing reason and acceptance checks. Luna is not a mandatory child default, and no price/savings claim follows from its capability label.
- **Explicit pins:** User pins override defaults. Lane `pinned` requires explicit provider, model, supported options and reason. Cross-harness work is an explicit exception, not an inherited accident. Never silently substitute or fall back; unavailable selection is a blocker.
- **Assignment and audit:** Supply `task`, `[sub] [topic] short goal` title, role and stable per-round `clientRequestId`, plus `lane` and `reason` when non-default. Include the objective, source references, constraints, owned paths, shared interfaces, deliverable and acceptance. The helper validates catalog selection, verifies resolved provider/model/options, cancels unverified launches and records routing metadata (not task bodies or credentials) in `${XDG_STATE_HOME:-~/.local/state}/cfg-init-t3/delegations.jsonl`. Retain task IDs and consume actual results; no polling.
- **Coordinator-only interaction:** Workers never spawn agents/threads, ask the user, open dialogs, resolve approvals or continue via direct user messages. Return `BLOCKED` with the question, options/tradeoffs, evidence and any required permission to the coordinator. Coordinator asks once in the main conversation and delegates a new bounded round with the answer. Do not send follow-up turns to the backing child thread. Security approvals are never assumed, auto-accepted or widened.
- **Runtime boundary:** The configured ACP relay rejects additional worker prompts and cancels worker question elicitations rather than displaying dialogs. Security permission requests and responses remain unchanged and host-owned; cfg-init cannot move those approvals into the coordinator UI. The OMP extension blocks native spawning and child interaction tools; helper refuses child delegation using host lineage. These are cooperative integration guards, not a sandbox for unrestricted shell code or other harnesses. T3's composer visibility is host-owned; do not claim this configuration hides it. Child chat-specific instructions are not inherited: include necessary constraints in every brief.
- **Verification:** Main exercises the consumer-visible path after integration. A completed child or favorable review is not acceptance. Check requested vs resolved selection and report unverified host boundaries explicitly.
